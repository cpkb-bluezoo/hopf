Scalability Audit

How hopf-core's thread-per-core (TPC) reactor architecture actually behaves as connection count, core count, and load grow — read directly from crates/hopf-core/src/, not from the marketing description in Architecture. Companion to Conformance and Performance.

Method

Everything below is sourced from reading crates/hopf-core/src/{reactor,runtime,accept,bufpool,storage,cmd,connection,timer,acl,quota}.rs directly — file:line citations throughout. This is a behavioral audit (what happens as N grows), not a benchmark: no load test was run to produce numbers. Where a claim would need a benchmark to become a number rather than a mechanism, that's said explicitly.

The scaling model in one picture

1 accept-loop thread  ──RR──▶  N reactor threads (worker_threads, default 2×cores)
        │                              │
   ACL + rate-limit               each owns: mio Poll, HashMap<Token,TcpConnection>,
   (single-threaded)               TimerQueue (BinaryHeap), its own mpsc command queue,
                                    its own Arc<BufferPool> (never shared cross-thread)

  M storage threads (StorageConfig::threads, default cores.max(4))
        │
   single shared Mutex<Receiver<Job>>, bounded SyncSender (queue_capacity=4096)

The design intent (per Architecture) is "each connection stays on one reactor for life... I/O, TLS, and protocol bytes never migrate mid-connection." That holds for everything on the reactor side, verified below — the one structure that sits outside per-core isolation is the single accept thread's ACL/rate-limit evaluation, discussed next.

Accept path: single-threaded by design

Every listener in the process — regardless of how many protocols or ports are composed together — is accepted by one AcceptLoop thread (crates/hopf-core/src/accept.rs:30-40, spawned once in runtime.rs:87-89). Its run loop (accept.rs:120-142) polls all registered listeners with a single mio::Poll, and for each readable listener drains accept() in a loop (accept.rs:199-251), evaluating the peer ACL (PeerAcl::allows, acl.rs:76-85) and rate limiter (AcceptRateLimit::try_acquire, acl.rs:130-162) inline before handing the stream to a worker via plain round-robin (accept.rs:253-258, next_worker()).

Consequence: connection setup rate (accepts/sec) does not scale with core count — it's bounded by one thread's ability to call accept(), evaluate ACL/rate-limit, and dispatch a ReactorCmd::Register. Once a connection is registered on its reactor, all further I/O for that connection does scale across cores (each reactor is fully independent from that point on) — this is only a bottleneck for the accept rate, not steady-state per-connection throughput. For workloads dominated by long-lived connections (IMAP IDLE, MQTT, WebSocket) this essentially never matters; for workloads with very high connection churn (short-lived HTTP/1.0-style requests, connection-per-poll clients) it's the first thing that would show up in a load test.

Round-robin dispatch (rr.fetch_add(1) % n, accept.rs:256) also means new connections are assigned ignoring each reactor's current load — a reactor doing heavy TLS handshake or protocol-parsing work for its existing connections keeps receiving new ones at the same rate as an idle reactor. There's no least-loaded or work-stealing dispatch.

On EMFILE/ENFILE (fd exhaustion), the accept loop sleeps 1 second (ACCEPT_BACKOFF, accept.rs:21,239-243) — this pauses accept processing for every listener in the process, not just the one that hit the limit, since it's the same single thread and loop iteration. Reasonable fail-safe against a busy-loop, worth knowing it's process-wide.

Buffer pool: per-reactor, no cross-thread lock

Each reactor thread constructs its own Arc<BufferPool> inside Reactor::spawn's thread closure (reactor.rs) — one pool per worker thread, never shared with any other reactor. BufferPool itself is a Mutex<Vec<Vec<Vec<u8>>>> (power-of-two size-class buckets, bufpool.rs:12-15), but because a connection is pinned to one reactor for life and every buffer acquire/release for that connection happens on that same reactor's thread, the lock is never contended between threads — only ever acquired and released by the single thread that owns it.

Every socket read that needs to grow net_in, every write that needs to grow net_out, and every connection's initial buffer allocation and final release call pool.acquire()/pool.release() (connection.rs:88-89,249-253,441-446,590-594,616-621), all on that one thread. This matches the "shared-nothing per core" framing in Architecture: buffer memory, like connection state and protocol bytes, stays entirely within one reactor's thread.

Per-connection reconciliation: O(1), not a per-tick scan

Every place a connection's state can change — handle_readable, handle_writable, and a WithConn command finishing (reactor.rs) — ends by calling sync_or_close with that one token: it looks the connection up once, and either closes it (close_conn) if it's no longer open or reregisters its mio interest if interest_dirty is set. register_connection does the equivalent check inline before a new connection is ever inserted. There is no pass anywhere in the reactor loop that iterates the whole HashMap<Token, TcpConnection> looking for connections that changed — reconciliation cost is proportional to how many connections were actually touched in a given tick (readable + writable + command-driven), never to how many connections the reactor happens to be carrying.

Cross-thread signaling: ConnHandle and wakeups

Every reactor has its own unbounded mpsc::channel for ReactorCmd (cmd.rs:142-151) — unlike the storage pool (see below), there is no bound and no backpressure here. ReactorHandle::send (cmd.rs:89-92) pushes onto the channel and calls Waker::wake() — one OS-level wake syscall per command, whether that's a ConnHandle::send (used by every cross-connection fan-out — MQTT broker publish being the clearest example), a scheduled timer, or an execute() task. There's no batching: N sends to the same reactor in a tight loop (e.g. an MQTT PUBLISH fanning out to many subscribers that happen to share a reactor) pay for N wake syscalls, not one.

The lack of a bound on the command channel is the flip side of StorageExecutor's deliberate bounded/fail-fast design (next section) — if a reactor's command producers (other threads, other reactors) ever outpace that reactor's ability to drain drain_commands() (reactor.rs:136-148, itself an unbounded drain-to-empty loop each tick), the channel grows without limit. This would require a reactor to be pathologically slow or stuck (e.g. a `ConnHandle::execute` closure that blocks, or a panic loop) rather than normal load, but there's no structural guard against it the way there is for storage submissions.

Storage pool: bounded and fail-fast (this one's right)

StorageExecutor (storage.rs:66-166) is the one place in the runtime that gets backpressure right: a fixed-size thread pool (default cores.max(4), storage.rs:51-60) draining a bounded mpsc::sync_channel (default capacity 4096). Submission uses try_send (storage.rs:136) — on saturation, the caller's callback is invoked immediately on the calling reactor with StorageError::Rejected (storage.rs:140-151) rather than blocking the reactor or queuing unboundedly. This is exactly the "fail-fast backpressure, never block the reactor" contract the docs promise, and it's implemented correctly.

The one shared point of contention is Receiver<Job> wrapped in a single Mutex (storage.rs:82,168-179) that all threads workers block on via recv() — standard single-queue thread-pool contention (a thundering-herd wakeup when a job arrives with multiple idle workers). For blocking filesystem/mailbox work this is a reasonable, common tradeoff; it would only matter at a submission rate high enough to make queue-lock contention comparable to the blocking work itself, which is a different regime than what this pool is for.

ACL, rate limiting, and quotas

PeerAcl::allows (acl.rs:76-85) is a linear scan over the allow/deny Vec<IpNet> lists, evaluated on the single accept thread for every accepted connection (accept.rs:208) — fine for typical ACL sizes (tens of entries), but combined with the single-accept-thread finding above, a very large CIDR list adds directly to that thread's per-accept cost with no way to parallelize it.

CounterQuota (quota.rs:44-95) is lock-free (plain AtomicU64 counters, Relaxed ordering — correct here since each axis is an independent monotonic counter with no cross-axis ordering requirement) and scales fine per-connection.

Unbounded growth vectors

AcceptRateLimit's per-source tracking is a HashMap<IpAddr, (u32, Instant)> (acl.rs:104) that is only ever inserted into, never pruned. try_acquire (acl.rs:130-162) reads or inserts an entry for the peer's IP on every accept, but nothing ever removes an entry once its rate-limit window has expired — get_mut either updates the existing entry or, on expiry, the _ => arm (acl.rs:156-159) overwrites it in place, which is fine for a repeat source, but a source that connects once and never returns leaves its entry in the map forever. For a listener with a configured per_source limit facing traffic from many distinct source IPs over the process lifetime — the exact traffic pattern a rate limiter exists to defend against (many distinct/spoofed/rotating sources) — this map grows without bound for the life of the process. This is the one finding in this audit that's a genuine unbounded-memory issue rather than a contention/throughput characteristic, and it's directly reachable from network input (any listener with per_source > 0 configured).

None of these findings are "hopf is broken" — the steady-state per-connection I/O path, which is what TPC is chiefly claimed for, holds up under reading. The accept-rate-limiter map is the one item worth fixing before calling the scalability story complete; the rest are honest tradeoffs worth documenting rather than defects.
