NNTP

hopf-nntp is an NNTP / NNTPS news reader server and async client (RFC 3977, STARTTLS per RFC 4642, AUTHINFO per RFC 4643). The server serves the mailboxes of a mailbox store as newsgroups, or any other source of articles through a handler, streaming every article in constant memory. The client dials, greets, reads CAPABILITIES, negotiates TLS and authenticates for you, then hands your handler a session that queues commands from any thread and answers through callbacks.

Server

NntpService registers a listener on a Runtime and serves reader mode only (no IHAVE, no NEWNEWS, no transit). By default each mailbox of a MailboxStore is a newsgroup: its name with the store's hierarchy delimiter written as . (the mailbox comp/lang/rust is comp.lang.rust), and a message's article number is its UID, so numbers never change and are never reused. A Maildir store always has an INBOX, which is listed as a group of that name. The store is opened for one user, news unless DefaultNntpHandlerFactory::with_store_user says otherwise, whoever the client authenticates as.

use std::sync::Arc;
use hopf_core::{Runtime, RuntimeConfig};
use hopf_mailbox::MaildirFactory;
use hopf_nntp::{NntpConfig, NntpService};

let rt = Arc::new(Runtime::start(RuntimeConfig::default())?);
let spool = Arc::new(MaildirFactory::new("/var/spool/news"));
let config = NntpConfig::new("0.0.0.0:119".parse()?, "news.example.com")
    .with_credentials(credentials)   // Arc<dyn CredentialStore>; AUTHINFO is offered
    .with_tls(acceptor);             // STARTTLS is offered
let service = NntpService::new(config, rt, spool);
let addr = service.start()?;         // service.stop() stops accepting

For NNTPS add .implicit_tls() to the configuration (and listen on 563). A service is not built from Composition XML: like POP3 and IMAP it needs the Runtime, so wire it with Composition::runtime() and Composition::listen_tcp(service.control_listener()). The listener's connection limits, ACL and accept rate limit apply as to any other.

A runnable version is examples/nntp (cargo run -p nntp). It has been run against Python's nntplib (every reader command, AUTHINFO USER/PASS and a post) and, for STARTTLS, OpenSSL's s_client -starttls nntp.

Commands

CAPABILITIES, MODE READER, DATE, HELP, QUIT, GROUP, LISTGROUP, LAST, NEXT, ARTICLE, HEAD, BODY, STAT, LIST (ACTIVE, NEWSGROUPS, OVERVIEW.FMT), NEWGROUPS, OVER and HDR (with XOVER and XHDR), POST, STARTTLS and AUTHINFO (USER/PASS and SASL). Wildmats (RFC 3977 section 4.2) are supported wherever a command takes one. A client may pipeline: commands are read one at a time and the bytes behind a command wait in the connection's ring until it has been answered, so answers come back in order.

Streaming and memory

Everything that touches the news runs on the runtime's storage pool, against a handler whose methods may block. A command writes its answer into a bounded pipe (16 KiB chunks, 128 KiB held) that the connection empties as its output drains, so a client that reads slowly slows the read of the store instead of the answer piling up in memory. A client that has not taken what is waiting for write_stall_timeout (default 120 s) is closed, and a client that goes away releases the storage thread at once. Articles are dot-stuffed by a state machine that holds no line, however long. A 192 MiB article peaks at about 127 KiB of heap, and posting one at about 149 KiB (tests/memory_bound.rs, a counting allocator).

Posting

POST answers 340 and the article then reaches a PostSink dot-unstuffed, in pieces of at most 64 KiB, never whole. One piece is written at a time and the connection reads no more of the client's article until the write has returned, so a store that falls behind slows the client. The stock sink keeps only the header block (up to 64 KiB) to read Newsgroups; it requires Newsgroups, From and Subject, adds a Message-ID and a Date if the article has none, files the article in each named group that exists, and streams the rest into them. An article that cannot be filed gets 441 with the reason, and nothing is kept; if the client goes away mid-article the appends are aborted. An article over max_post_size (default 64 MiB, None for no limit) is read, thrown away and refused. Posting is refused with 440 when posting_allowed is false, and a store that cannot append refuses the post.

TLS and authentication

  • STARTTLS is offered when an acceptor is configured and the connection is neither encrypted nor authenticated. A client that sends bytes ahead of the handshake is disconnected, and after the handshake the server forgets what the client had selected (RFC 4642 section 2.2.2).
  • AUTHINFO USER/PASS and AUTHINFO SASL run against the CredentialStore given to with_credentials, on the storage pool. The mechanisms offered are those the store supports. A password, or a mechanism that sends one in the clear, is refused with 483 and not advertised on a connection that is not encrypted, unless allow_cleartext_auth is set; SCRAM is offered either way. EXTERNAL is offered only when the client presented a certificate.
  • require_authentication answers every command that reads or posts news with 480 until the client has authenticated.
  • A connection whose credentials are refused max_auth_failures times (default 3, 0 for no limit) is closed with 400. There is no delay between attempts and no lockout across connections; put an access control rate limit in front if you need one.

Handlers

The stock handler can be replaced to serve any other source of articles. NntpHandlerFactory::create makes a ClientConnected for each connection, which accepts it (naming the greeting and giving the ReaderHandler) or refuses it. ReaderHandler has the news: select_group, article_numbers, locate_number, locate_message_id, read_article (the article's octets, given to a callback that says whether the server wants more), groups, and optionally new_groups, begin_post (returning a PostSink), authorize, and summarise / overview, which by default read the article. Its methods run on the storage pool and may block.

Metrics

Process-local NntpServerMetrics via NntpService::metrics(): connections, commands, articles retrieved and posted, authentications, STARTTLS upgrades. With NntpService::with_telemetry(&pipeline), hopf_otel::NntpServerMetrics emits nntp.server.connections, nntp.server.active_connections, nntp.server.session.duration (ms), nntp.server.commands (nntp.command), nntp.server.auth (mechanism, result), nntp.server.articles and nntp.server.article.duration (nntp.article: retrieved or posted, and outcome), nntp.server.bytes_sent (per connection, when it closes) and nntp.server.starttls. With traces enabled each connection is a trace, ARTICLE, HEAD, BODY and posts are spans in it, and handlers find the W3C traceparent in NntpConnectionMetadata.

Session API

NntpClientHandler::on_connected(&NntpSession, &NntpGreeting) fires once the session is usable; the greeting carries the capabilities, whether posting is allowed, and whether the connection is secure and authenticated. Clone the NntpSession and keep it: commands may be queued from any thread, go out one at a time in queue order, and each completion callback receives the final NntpStatus (or the transport error that ended the session, which every still-queued command also hears). quit() sends QUIT and closes once it is answered; is_alive() is false after that or once the connection is gone.

Callbacks run on the connection's reactor thread: hand the data to another thread rather than doing slow work inside them.

Quick start

use std::sync::Arc;
use hopf_core::{public_trust_connector, Runtime, RuntimeConfig};
use hopf_nntp::{NntpClient, NntpClientHandler, NntpGreeting, NntpSession};

struct Headlines;

impl NntpClientHandler for Headlines {
    fn on_connected(&mut self, session: &NntpSession, greeting: &NntpGreeting) {
        println!("secure={} posting={}", greeting.secure, greeting.posting_allowed);
        let s = session.clone();
        session.group("comp.lang.rust", move |g| {
            let g = g.expect("GROUP");
            s.over(g.last.saturating_sub(20), g.last, |o| println!("{} {}", o.article_number, o.subject), |_| {});
            s.quit();
        });
    }
    fn on_error(&mut self, error: &std::io::Error) {
        eprintln!("nntp: {error}");
    }
}

let rt = Arc::new(Runtime::start(RuntimeConfig::default())?);
NntpClient::new("news.example.com", 563)
    .implicit_tls(public_trust_connector(&[]), "news.example.com")
    .credentials("alice", "secret")
    .connect_with(&rt, Box::new(Headlines))?;

Posting and attachments

NntpSession::post takes an article already in memory. For one that is not, post_stream takes an NntpPoster: once the server has said 340, next(&mut NntpPostStream) is called on the reactor to write the next piece (any line ends; dot-stuffing, the CRLFs and the terminating dot are added), and called again only when the connection has taken what the last call wrote, so a poster that writes a chunk a call holds no more than that. It returns PostStep::More, Done, Failed(error), or Wait when its data is coming from another thread, which then calls the PostWaker from NntpPostStream::waker(). A poster that fails closes the connection (a half-sent article cannot be abandoned) and the post's callback hears the error. post is a poster over a slice, so there is one way an article is sent.

post_with_attachments(text, attachments, ...) follows the text with each NntpAttachment as a uuencoded block (from_path, from_bytes, from_reader or from_source for a source of your own; mode sets the permissions in the begin line). Each attachment is read and encoded on a thread of its own, two pieces ahead of the connection at most, so the reactor never blocks and none is held whole. In the other direction article_with_attachments and body_with_attachments take an NntpArticleHandler that is told the text and, apart from it, each file (attachment_begin(mode, name), attachment_data, attachment_end(complete)) as the article arrives, found by rmimeparser's UuScanner. Posting a 128 MiB article, or one with a 128 MiB attachment, to a hopf server and reading it back takes the same heap as a small one (tests/memory_bound.rs).

Errors

NntpClientHandler::on_error reports a refused or timed-out dial, a TLS failure, a required STARTTLS the server did not offer, rejected credentials (PermissionDenied, with the server's 481/482 text), a command that got no reply within the budget, or the transport going away mid-session. A command the server rejects is not a session error: its own callback gets NntpClientError with the status code and text.

Limitations

  • Server: reader mode only. OVER reads each article in full to count :lines, which RFC 3977 requires to be exact, so an overview of a large range is slow with the stock handler; a handler with the figures indexed answers faster by overriding summarise or overview.
  • Server: the stock handler does not know when a mailbox was created, so NEWGROUPS lists nothing, and a message-id that is not in the selected group is found by opening every group in turn.
  • Server: duplicate Message-IDs are not detected on a post.
  • Client: wildmat matching, overview formats beyond the default eight fields, and LIST OVERVIEW.FMT are left to the application, and one command is in flight at a time (no pipelining). ARTICLE, HEAD, BODY and STAT take an article number, not a message-id.
  • Integration tests (--features integration) run the client against a scripted server and against the real server (tests/roundtrip.rs).
