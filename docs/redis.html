Redis

hopf-redis is an async Redis and Valkey client speaking RESP2 and RESP3. One RedisClient is one pipelined connection bound to a reactor: commands go out at once from any thread, and each reply comes back as a callback on the reactor.

Quick start

use hopf_core::{Runtime, RuntimeConfig};
use hopf_redis::{RedisClient, RedisConfig};

let rt = Runtime::start(RuntimeConfig::default())?;
let redis = RedisClient::connect(rt.pick_worker(), RedisConfig::new("redis.example.com", 6379));

redis.set("greeting", "hello", |r| assert!(r.is_ok()));
redis.get("greeting", |r| println!("{:?}", r));      // Ok(Some(b"hello"))
redis.incr("visits", |r| println!("{:?}", r));       // Ok(1)

Every method returns at once and calls its callback exactly once, on the reactor the client was bound to, and never before the call that issued it has returned. The callbacks of one client run in the order the replies arrive, which is the order the commands were issued.

Connecting

RedisClient::connect(&reactor, config) dials at once. A host name is resolved through hopf-dns (a resolver made on the client's reactor from the system's nameservers, unless RedisConfig::resolver gives one); a literal address is used as it is. On the new connection the client negotiates and authenticates before any command runs:

  1. HELLO 3, with AUTH (user default unless username is set) and SETNAME when configured. The reply tells the client RESP3 is in use (is_resp3()).
  2. A server that does not know HELLO (Redis before 6.0; a proxy that does not carry it) answers an error, and the client starts again in RESP2: AUTH, CLIENT SETNAME. A refused password (WRONGPASS, NOAUTH) is not a reason to fall back: it fails the connection.
  3. SELECT for a non-zero database.

Commands issued before this is done wait, and are sent in order when the connection is ready, so a command never runs unauthenticated. resp2_only() skips HELLO.

Commands

Typed helpers return the reply as the type the command returns, with a nil as None: strings (get, set, set_with(SetOptions), setnx, getdel, mget, mset, incr, incrby, decr, decrby, append, strlen), keys (del, exists, expire, pexpire, ttl, pttl, persist), hashes (hset, hget, hmget, hgetall, hdel, hexists, hincrby, hlen), lists (lpush, rpush, lpop, rpop, llen, lrange, lindex), sets (sadd, srem, smembers, sismember, scard), sorted sets (zadd, zrem, zrange, zrange_withscores, zscore, zincrby, zcard), scripts (eval, evalsha, script_load) and the connection (ping, auth, auth_user, select). SetOptions { nx, xx, ex, px, exat, pxat, keepttl } covers SET's modifiers.

Anything else goes through command(&[words], callback) or send(&Command, callback) and comes back as a Value: Null, Int, Simple, Bulk, Array, and, from RESP3, Map, Set, Double, Bool, BigNumber, Verbatim, Push. An error reply to a command is Err(RedisError::Server) with its code (WRONGTYPE, MOVED, ...); an error inside an array (one command's result in a transaction) stays a Value::Error.

Pipelining and failure

A command is written when it is issued, without waiting for the replies to those before it; replies are matched to commands in the order sent, which is all RESP gives. One connection therefore carries many commands in flight from any number of threads. send_batch writes several commands together with nothing from another caller between them.

  • Connection lost. A command sent and unanswered fails with ConnectionLost and is not sent again: it may have run, and most commands are not safe to repeat. The next command dials a new connection.
  • Failed connect or handshake. Commands waiting for it fail (Connect, or the server's own error for a refused password). Then, for a growing time, new commands fail at once instead of each dialling again.
  • Timeout. The command fails with Timeout once; its reply, if it comes, is discarded in its place, so it cannot be mistaken for the reply to the command behind it. (A command that blocks the connection, such as BLPOP, holds up everything behind it until it returns; give blocking commands a connection of their own.) send_with_deadline(command, Deadline::After(d)) gives one command its own timeout, longer or shorter than command_timeout, whether or not that is set; Deadline::Never gives it none, for a command the server holds for as long as it likes. RedisCluster::send_with_deadline does the same, applied to each try.
  • A connection that has gone dead. A route that is black-holed, or a server that is paused or partitioned, sends no reset and no close, so the connection looks fine while every command on it waits out its timeout. While replies are owed and nothing at all has arrived for ping_interval, the connection is closed: what it owed fails with ConnectionLost and the next command dials afresh. Traffic of any kind counts as life, and a connection with nothing owed is never closed. No PING is sent first: replies come back in the order commands were sent, so a probe queued behind an unanswered command would be answered only after it. A command given no limit, or a longer one than command_timeout, is not checked while it is outstanding, since a server holding a blocking command or a WAIT says nothing meanwhile; with command_timeout(None), no connection is checked while it owes anything.
  • Close. close() fails what is waiting with Closed, and so does every later command.

Transactions and scripts

transaction(commands, callback) writes MULTI, the commands and EXEC as one batch, so nothing from another caller can come between them on the shared connection. The callback gets each command's result in order, or None if EXEC was aborted by a watched key. A command that fails when it runs is a Value::Error in the list; one refused when queued fails the transaction with that error.

watch, unwatch, multi, exec and discard act on the connection, which every user of a client shares, so another caller's commands can run in between. For a watch-then-transact sequence use a client of your own. eval and evalsha run a script; EVALSHA answers NOSCRIPT for one the server has not seen, so script_load it and try again.

Publish/subscribe and pushes

A connection that has subscribed gets messages when someone publishes, not replies, and in RESP2 the server refuses it ordinary commands. Subscriptions therefore live on a dedicated connection, a RedisSubscriber, and a RedisClient refuses SUBSCRIBE and its relatives with RedisError::Unexpected rather than let the server's pushes put every later reply out of step. Publishing is an ordinary command: RedisClient::publish and spublish return how many subscribers received the message.

use hopf_redis::{Message, RedisSubscriber, SubscriberHandler, SubscriptionChange};

struct Handler;
impl SubscriberHandler for Handler {
    fn on_message(&mut self, m: Message) { /* Channel, Pattern or Shard */ }
    fn on_subscription(&mut self, c: SubscriptionChange) { /* acknowledged, with the count */ }
    fn on_connected(&mut self, reconnect: bool) {}
}

let sub = RedisSubscriber::connect(rt.pick_worker(), RedisConfig::new("redis.example.com", 6379), Handler);
sub.subscribe(&["news"]);
sub.psubscribe(&["alerts.*"]);
sub.ssubscribe(&["orders"]);          // shard channels, Redis 7
// A closure is a handler that wants only messages:
let sub = RedisSubscriber::connect(reactor, config, |m: Message| println!("{m:?}"));
  • It keeps itself subscribed. The subscriber dials when created, and again whenever the connection is lost (after a growing pause, so a server that drops it at once is not hammered). It remembers what it was asked to subscribe to, and sends it all, one command per kind, on every new connection. subscribe, psubscribe and ssubscribe may be called before the connection is up; the unsubscribe forms (with no names: all of that kind) forget as well as send. on_connected(reconnect) says a connection is up and subscribed; on_disconnected that an established one ended. Messages published while it was down are not delivered: Redis does not keep them.
  • It notices a dead connection. With ping_interval (default 30 s) a connection that has gone quiet is sent a PING, and one that has said nothing for three intervals is dropped and dialled again. Traffic of any kind counts as life.
  • Both protocols. RESP3 sends messages and acknowledgements as pushes, RESP2 as arrays; both arrive as the same Message and SubscriptionChange events, in the order the server sent them. An error reply, such as NOPERM for a subscription an ACL forbids, comes to on_error.
  • Nothing is dropped. Out-of-band data of a kind the crate does not interpret reaches on_push as a Push { kind, data }.

RedisClient::set_push_handler receives the RESP3 pushes a command connection gets: key invalidations after CLIENT TRACKING on (Push::invalidation() says which keys, or everything after a flush), and anything else a server pushes, of any kind. Replies stay matched to their commands around a push. With no handler set, pushes are discarded.

Cluster

RedisCluster is the same client for a Redis Cluster or Valkey Cluster. Give it one or more seed nodes; it asks them for the layout (CLUSTER SHARDS, or CLUSTER SLOTS for a server without it), keeps a pipelined connection to each master, and sends every command to the master that owns the slot its key hashes to. Every typed helper of RedisClient is there, with command, send and transaction, and callbacks run on the reactor it is bound to.

use hopf_redis::{ClusterConfig, RedisCluster};

let cluster = RedisCluster::connect(
    rt.pick_worker(),
    ClusterConfig::new([("10.0.0.1", 7000), ("10.0.0.2", 7000)])
        .node_config(|c| c.password("secret")),   // every node connection
);
cluster.set("user:42", "ada", |r| assert!(r.is_ok()));
cluster.get("user:42", |r| println!("{r:?}"));
  • Routing. The slot is CRC16 of the key (or of the part inside the first {hash tag}) modulo 16384. The key positions of a command come from a table covering the commands Redis and Valkey define, including EVAL's numkeys, XREAD ... STREAMS and SPUBLISH's shard channel. For one it does not know, command_for_key names the key. A command with no key goes to any master in turn.
  • Several keys. They must share a slot, so use hash tags ({user:42}:profile, {user:42}:cart). Otherwise the command fails at once with CROSSSLOT, as the server would, without touching the network. transaction takes the same rule and runs on the owner of its slot; eval and evalsha use the keys they are given. command_for_key(routing_key, command, callback) picks the node by an explicit key, for a command the table does not know or one that must run where a particular key lives.
  • Redirections. MOVED updates the slot and refreshes the whole layout, and the command is sent again to the new owner. ASK sends that one command, preceded by ASKING in the same write, to the node the slot is moving to, and leaves the layout alone. Each hop spends one of max_redirects (default 5).
  • Failover. A node that cannot be connected to is dropped, the layout is fetched again and a command that was never sent is tried where its slot now lives. A command that was sent when its connection failed is not sent again; it fails with ConnectionLost and the layout is refreshed. CLUSTERDOWN (the slot has no master for the moment, as in the middle of a failover) and TRYAGAIN mean the command did not run, so the layout is fetched again and it is tried once more, up to max_redirects times, before the error is the caller's. A node that stops being a master is let go of once the commands already sent to it are answered.
  • A node that goes quiet. The connection's health check (see pipelining and failure) closes it after ping_interval of silence while replies are owed, and the cluster fetches the layout again whether or not any command was still waiting to hear of it. A command that merely times out does not ask for a new layout: a slow node is not a moved one.
  • Pushes. set_push_handler(|node, push| ..) receives the RESP3 pushes the node connections get, with the address of the node each came from: key invalidations after CLIENT TRACKING on (Push::invalidation()), and any other kind a server pushes. It applies to every node connection, those made before it was set and those made later (a node found by a refresh, or reached through MOVED or ASK), and to one that replaces another. clear_push_handler() stops it; with none set, pushes are discarded. Tracking belongs to a connection, so the application turns it on where it wants it with send_to_node(&node, &command, callback) (the node must be a master in the current layout) or send_to_masters(&command, |node, reply| ..), and again on a connection that is replaced, since the server forgets it with the old one; a node that stops being a master is let go of, and what was tracked on it with it. Subscription messages do not come here: they belong to a RedisSubscriber.
  • Refreshing. One at a time, and at most one in min_refresh_interval (default 500 ms) however many commands ask. refresh() asks for one, refresh_count() says how many have been made, and owner_of(slot), masters() and slot_of(key) expose the layout.
  • Per-node settings. node_config takes the RedisConfig template for every node connection: password and user, TLS connector, timeouts, RESP version. tls_server_name names the certificate to verify when the nodes are reached by address.

Publish/subscribe does not go through RedisCluster: it refuses SUBSCRIBE and its relatives like a command connection, and its push handler is for pushes no subscriber consumes. A RedisSubscriber pointed at one node receives that node's classic messages (which a cluster broadcasts to every node), and spublish on the cluster is routed by the shard channel's slot.

WAIT and WAITAOF

WAIT numreplicas timeout reports how many replicas have acknowledged every write made on the connection it is sent on, so it means something only on the master that took the write and on the connection that carried it. A cluster client that sent it to any master would get an immediate, meaningless count. wait_replicas(slot_key, num_replicas, timeout_ms, callback) does it properly; the callback gets the number of replicas that acknowledged, and fewer than asked for is Ok(n), not an error.

// a single-slot script on {order:7}-tagged keys, then confirm it reached a replica
cluster.eval(script, &["{order:7}:items", "{order:7}:total"], &[args], |r| { /* ... */ });
cluster.wait_replicas("{order:7}", 1, 100, |r| match r {
    Ok(n) if n >= 1 => { /* a replica has it */ }
    Ok(_) => { /* unconfirmed after 100 ms: treat the write as at risk */ }
    Err(e) => { /* connection lost, or the cluster is down */ }
});
  • Bound to the last command for the slot. If that command is still unanswered, the WAIT is written on the same connection straight behind it. If nothing is in flight it goes to the connection that serves the slot now. It is bound to a slot, so pass the key of the write (or its hash tag); WAIT calls for different slots each reach their own master.
  • If the write is redirected (MOVED or ASK) the WAIT goes with it and is written behind it on the node that takes it; the first node's answer is thrown away, so a count never comes from a connection that did not carry the write.
  • Never sent again. If the connection is lost, or the node leaves the layout, before the reply, the callback gets the error and nothing sends the WAIT anywhere else. CLUSTERDOWN is the callback's, not retried.
  • Deadline. The server holds the reply for up to timeout_ms, so the client's deadline is the node's command timeout plus timeout_ms; the callback gets Timeout once and a late reply is discarded. With timeout_ms 0 the server waits for ever and there is no client deadline, so pass a positive value.
  • wait_aof(slot_key, num_local, num_replicas, timeout_ms, callback) is WAITAOF in the same way, answering (local, replicas). A server answers an error for num_local 1 when it is not running with appendonly yes.
  • command_for_key(routing_key, &command, callback) sends any command, keyless ones included, to the master of the key's slot (CROSSSLOT if the command's own keys are elsewhere), and follows MOVED and ASK. A WAIT or WAITAOF sent through it is bound as above; one sent through command or send with no routing key fails at once, without being sent.

On a single server, RedisClient::wait_replicas and wait_aof take the same arguments (the key is ignored) and run a plain WAIT with the same deadline. The connection is shared by every user of the client, so what a WAIT confirms is all the writes on it so far, which includes yours and can be more. If a MULTI is open on the connection they fail at once without sending anything, because the server would queue the WAIT instead of running it. A cluster has no connection-wide MULTI: transaction is one batch.

TLS

use hopf_core::ClientTlsBuilder;

let tls = ClientTlsBuilder::new()
    .trust_anchors([ca_der])                 // or .public_trust() (the default)
    .client_credentials(client_identity)     // mutual TLS, if the server asks
    .build();
let redis = RedisClient::connect(rt.pick_worker(), RedisConfig::new("redis.example.com", 6380).tls(tls, "redis.example.com"));

The connector verifies the server's certificate against server_name. See TLS: ClientTlsBuilder.

The RESP codec

hopf_redis::resp is usable on its own. RespParser is a push parser: feed(&mut data, &mut sink) takes bytes in any split, consumes all of them, and hands each reply to the sink the moment its last byte arrives. It keeps no input: a header line in progress is a small scratch buffer, a bulk payload is appended to the value it becomes, and aggregates wait on an explicit stack, so nesting depth is a limit, not a stack overflow. RESP3 attributes are read and dropped. RespLimits bounds what a server may make the parser hold, and each size is checked when it is announced, before memory is reserved for it:

LimitDefaultBounds
max_bulk512 MiBone bulk, verbatim or error string (Redis's own proto-max-bulk-len default)
max_aggregate226elements an aggregate may announce
max_depth32aggregates inside aggregates
max_line64 KiBa header or simple-string line
max_reply_bytes1 GiBone whole reply

A violation is an error and the connection is closed. encode_command writes a command as an array of bulk strings.

Testing

The codec, the key table and the layout parsers have unit tests with no I/O, including every reply type split at every byte boundary. --features integration adds suites with real sockets. scripted runs the client against a scripted RESP server inside the test: an old server without HELLO, a wrong password, a drop mid-pipeline, a stray reply, a slow handshake, a timed-out command with another behind it, a black-holed connection and handshake, a node that goes dark and is failed over from, pushes on node connections, a server that appears later, TLS, an unknown push kind, a silently dead subscriber connection and a subscriber that is dropped and must subscribe again. cluster_scripted does the same for scripted cluster nodes, including WAIT behind an in-flight write, redirected with it, and lost with its connection. redis_server and pubsub_server run against a real server named by HOPF_TEST_REDIS (and HOPF_TEST_REDIS_AUTH, a server started with --requirepass hunter2), and cluster_server against a cluster named by HOPF_TEST_CLUSTER (one node's host:port; three masters, nodes announcing addresses the test can reach). A test with no server named is skipped. They have been run against Redis 7.4 and Valkey 8.1:

podman run -d --rm -p 127.0.0.1:16379:6379 docker.io/library/redis:7
podman run -d --rm -p 127.0.0.1:16380:6379 docker.io/library/redis:7 redis-server --requirepass hunter2
HOPF_TEST_REDIS=127.0.0.1:16379 HOPF_TEST_REDIS_AUTH=127.0.0.1:16380 \
    cargo test -p hopf-redis --features integration

The cluster tests move empty slots between masters (and put them back) to provoke MOVED and ASK. One more fails a master over to its replica with CLUSTER FAILOVER and back, with every other test held off meanwhile; it changes the cluster's roles, so it runs only when HOPF_TEST_CLUSTER_FAILOVER is also set and every master has a replica. Redis will not vote for a second failover of the same master within twice its node timeout, so two runs in quick succession make the second wait out the 30 seconds. The WAIT tests check against CLIENT LIST which connection ran the WAIT.

Limitations

  • Publish/subscribe has no cluster mode: a RedisSubscriber connects to one node, so a shard-channel subscriber has to be pointed at the node that owns the channel's slot, and does not follow it if the slot moves.
  • Commands are sent to masters only; there is no reading from replicas (READONLY).
  • One connection per client, and one per master in a cluster. Spread load by creating clients on several reactors; there is no pool.
  • A command that was sent when a connection was lost is not retried.
  • No URL form of the configuration (redis://, rediss://).
