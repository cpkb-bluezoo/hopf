Architecture

Hopf is a thread-per-core multi-protocol networking framework on mio. Listen and dial are equal bindings on one Runtime, and server and client are equal roles in every protocol crate. Protocol code sees plaintext handlers and Streams; TLS, QUIC, buffers, affinity and backpressure stay below that line. Inbound bytes live in fixed-size LoopBuf ring buffers that handlers read in place.

Purpose

The default topology is a graph of endpoints on one Runtime: N listeners and M dialers in one process are normal (peer / P2P compositions), not a third stack. A process may be a server, a client, a proxy or any mixture, and clients routinely host several protocols together - at minimum DNS under dial, so that a hostname can be resolved on the reactor that will own the connection.

Many Internet application protocols share the same transport model: TLS or QUIC where appropriate, transport-level backpressure, worker and storage pools independent of connection count, and one buffer model. Hopf provides that model once, in hopf-core, and every protocol crate plugs into it from either side of a connection.

The buffer model is the loopbuf ring: a connection owns a fixed-size ring for its inbound bytes, the protocol handler reads it in place and consumes whole tokens, and what it leaves behind is presented again with the next arrival. Neither the framework nor a handler accumulates a stream of unbounded size. See Buffers and backpressure.

Thread-per-core

  • Each connection is owned by one reactor thread for its lifetime (affinity), whether it was accepted or dialled.
  • I/O, TLS and protocol byte handling stay on that thread.
  • Application, blocking and storage work runs on a separate storage pool.
  • Cross-core coordination is explicit (ConnHandle, execute, message passing), not implicit task migration.
  • A panic in a handler is caught at the connection boundary: it is logged and that connection is closed; the reactor carries on.
Piece Role
Accept loop Binds TCP and UNIX sockets, applies ACL, peer-credential and rate-limit policy, round-robins accepts onto workers
Worker reactor Owns connection affinity; timers, TLS I/O, UDP datagram sockets, execute hops. Defaults to twice the available parallelism (minimum 2)
Dial RR Separate round-robin for outbound connects (Runtime::connect, connect_unix)
StorageExecutor Bounded blocking pool; results hop back via Endpoint::execute / ConnHandle; fails fast when full
QUIC driver A hopf-quic thread owning the UDP socket and the QUIC state machine; still exposes an Endpoint per bidirectional stream, so protocol handlers do not know they are on QUIC. TLS 1.3 only, PQC-first hybrid ML-KEM key exchange
Pool hopf_core::Pool: protocol-agnostic keyed reuse of live ConnHandles for client facades that want keep-alive; whether to pool at all stays a per-protocol decision

Optional future: io_uring completion paths for Linux behind the same Endpoint / handler traits - an evolution, not a requirement.

I/O substrate (mio)

Build on mio (epoll / kqueue readiness) with an in-tree executor, timer and registration model. Hopf uses mio only, not the Tokio runtime.

This preserves the readiness mental model (interest ops, fill a buffer, parse, write queue, backpressure), portable development (including macOS), and a near-zero dependency surface for the reactor.

Accept loops, per-core reactors, timers, cross-thread queues, buffer pools and the listen/dial APIs are implemented in-tree. The pattern for all I/O is reactor and callback.

Buffers and backpressure

There is one buffer model for every byte-stream protocol, defined in hopf-core and shared by TCP, TLS, QUIC streams and the HTTP adapters.

Buffer What it is
Wire ring (net_in) A LoopBuf that the reactor reads the socket into. Its size is fixed for the life of the connection: max_net_in rounded up to a power of two, never less than 32 KiB (a TLS record is up to 16 KiB and must fit whole). Holds ciphertext when TLS is active, plaintext otherwise.
Plaintext ring (app_in) Only on a TLS connection: a 64 KiB LoopBuf that records are decrypted into. The reactor decrypts a record only when the ring has room for the plaintext it may hold, so a slow handler stalls the connection rather than growing memory.
Outbound buffer (net_out) A pooled byte buffer that Endpoint::send(&[u8]) appends to and the reactor drains when the socket is writable. It is capped by max_net_out; a connection that exceeds the cap is closed and the handler is told why.
Buffer pool BufferPool recycles rings and outbound buffers in power-of-two size classes so that connection churn does not hit the allocator.

The receive contract

ProtocolHandler::receive is handed the connection's ring itself, not a copy and not a borrowed slice cursor:

fn receive(&mut self, endpoint: &mut dyn Endpoint, buf: &mut LoopBuf);
  • Consume only whole tokens. Call buf.advance(n) for what you have fully processed. Anything left in the ring is presented again, at the front, on the next call once more bytes have arrived.
  • Hold none of the stream yourself. A handler keeps bounded parser state (a verb, a partially read number), never a growing copy of the input. Message bodies are passed on as they arrive, not collected.
  • The ring can wrap. buf.readable_spans() returns the readable bytes as up to two slices. hopf_core::take_crlf_line reads a CRLF-terminated line across the wrap, and hopf_core::with_slice lends a single contiguous slice to a parser that wants one (copying only if the ring has wrapped).
  • A token that can never fit is an error. If the ring is full and the handler consumed nothing, the token is larger than the ring will ever hold. Report it with Endpoint::fail; do not start buffering.
  • Backpressure is automatic. While the ring is full and the handler is not consuming, the reactor stops reading the socket. Handlers can also call pause_read / resume_read explicitly (for example while a storage operation is in flight) and use on_write_ready to wait for the outbound buffer to drain.
fn receive(&mut self, endpoint: &mut dyn Endpoint, buf: &mut LoopBuf) {
    // A partial line stays in the ring until its CRLF arrives.
    while let Some(line) = hopf_core::take_crlf_line(buf) {
        self.on_command(endpoint, &line);
    }
}

Egress is deliberately simpler: send(&[u8]) copies into the outbound buffer, which is capped, so a handler that produces faster than the peer reads is stopped by the cap or by on_write_ready. Callbacks that deliver application payload to user code (an HTTP body chunk, a WebSocket message fragment) hand out slices of the ring or of a decoded frame; they are consumed during the call.

Storage and DNS

mio covers sockets, not arbitrary filesystem I/O. Mail, FTP, WebDAV and large body paths use an explicit storage executor: blocking or off-loop file work, never on the reactor thread. A handler pauses reads, submits the operation, and resumes from the completion callback, which runs back on the connection's own reactor.

Name resolution is a substrate in hopf-dns, not a bolt-on product, and every dialling crate uses it:

  • A reactor-affine DnsResolver (sockets, pending queries and timers on that core), with process-shared configuration and a TTL cache where appropriate.
  • Dial-by-name resolves on the target reactor; the callback runs there, then dials TCP or QUIC.
  • Upstreams may be UDP, TCP, DoT, DoQ or DoH, ranked by a capability cache; public WebPKI trust is built in for encrypted upstreams.
  • No blocking getaddrinfo on reactor threads.

See DNS and runtime options.

Transport vs HTTP Stream

Layer Concepts
A - Transport (hopf-core / hopf-quic) Endpoint (byte stream); TCP; UNIX sockets; UDP datagrams; QUIC stream endpoint; multiplexed QUIC connection
B - HTTP Stream (hopf-http) One request/response exchange; HttpStream + ServerHandler / ServerWriter, ClientHandler / ClientWriter - version- and transport-agnostic

H1 adapts a TCP Endpoint into serialised Streams; H2 multiplexes Streams on one TCP Endpoint; H3 maps each request to a QUIC stream Endpoint. Bind vs dial only affects how the transport was born; server/client role is a separate axis. Terminology: HTTP Stream is not an H2 stream id and not a QUIC stream endpoint.

Endpoint vs ProtocolHandler

Type Role
Endpoint Transport face: send, close, fail, start_tls / start_client_tls, pause_read / resume_read, on_write_ready, execute, schedule_timer, handle (a cloneable ConnHandle), local and remote addresses, PROXY protocol TLVs, security_info
ProtocolHandler Protocol state machine: connected, receive(&mut LoopBuf), disconnected, security_established, drain, error, plus migrated (QUIC path change) and datagram_received (QUIC / HTTP/3 datagrams) with default no-op bodies

HTTP adapters (H1Endpoint, H2Endpoint, CleartextHttpEndpoint, AlpnHttpEndpoint, H3 handlers) are ProtocolHandlers that drive Stream handlers; H1 and H2 parse straight out of the connection ring, and H3 and QUIC streams read from fixed rings of their own. connected runs on the worker reactor once the socket is registered (and, on a PROXY protocol listener, once the header has been parsed); a protocol that must wait for TLS defers its greeting to security_established.

Both reduce to registering a stream on a reactor with lifetime affinity, and both share TcpConnParams (buffer caps, idle timeout, TLS). Listeners add what only a listener needs: ACLs, rate limits, PROXY protocol and peer-credential checks.

Module layout: server and client as peers

Within a protocol crate, server (bind) and client (dial) are equal: neither is the unmarked default with the other bolted on. This is a module-layout axis distinct from the listen/dial API axis above - it governs where code lives, not how a socket was born. Three layouts are legitimate, chosen per crate by how tightly client and server share wire state:

Layout When to use it
Sibling modules
client/, server/, shared code at crate root		 Client and server are separate objects with separate state machines. Examples: hopf-dns (client/, server/, shared wire/, cache.rs), hopf-http, hopf-smtp, hopf-pop3, hopf-imap, hopf-ftp, hopf-mqtt. Smaller crates use sibling files instead of directories (hopf-grpc's client.rs and server.rs, hopf-socks, hopf-masque).
Role-parameterised file
one type/file, constructed as either role		 Client and server share one wire state machine and splitting it would fragment that machine. E.g. hopf-core::tls (acceptor_from_pem / connector_from_pem), hopf-quic (listen_quic / connect_quic), hopf-http's H1Endpoint::server() / ::client(), hopf-websocket's WsUpgradeHandler::server() / ::client(), and each hopf-auth SASL mechanism (PlainServer / PlainClient in one file; SASL client and server are wire roles, see auth).
Single role
no split, one role only		 The protocol has no counterpart role in-tree: client-only hopf-redis, hopf-amqp, hopf-amqp1, hopf-ldap and hopf-otel (an exporter; Hopf does not run a collector); server-only hopf-webdav (a filesystem handler); and hopf-mailbox (a storage backend, not a network protocol).

Because the roles are peers, the same crate can sit on both ends of one process: hopf-smtp accepts mail and relays it onward through its own client, hopf-socks and hopf-masque terminate a tunnel and dial the target, and hopf-mqtt runs a broker next to a client.

Dynamic bindings and composition

All bindings are dynamic. Listen and dial are added and removed through Runtime APIs while the process is alive. Configuration is a script over those APIs (Rust main / builder, or XML). Service orchestrates lifecycle; it does not own an immutable listener list as source of truth.

  • Canonical: Rust Composition builder.
  • Declarative: XML via tractrix to the same builder; closed registry of handler and trust names, no reflective DI.
  • TOML/YAML are not primary composition formats.

Details: composition, services, clients.

Lifecycle: readiness and drain

  • Runtime::is_ready is true while the runtime is not draining and every listener registered so far was bound; after a failed bind it stays false (bind_failures counts them), so a readiness probe can answer from it.
  • Runtime::start_drain stops accepting on every listener, makes is_ready false and calls ProtocolHandler::drain on every open connection, once each. A handler uses it to say goodbye in its own protocol (SMTP 421, POP3 or IMAP BYE, HTTP Connection: close or GOAWAY) and close.
  • Runtime::shutdown_graceful drains, waits up to RuntimeConfig::drain_timeout (default 30 s) for connections to finish, returning as soon as none is left, then closes what remains by force and stops the threads.

Auth vocabulary

Prefer TrustPolicy + IdentityMaterial over Realm-as-root naming. Attach to both listen and dial. SASL client/server are wire roles, independent of listen/dial. See auth.

Codec style

Grammar-driven incremental codecs: each protocol owns a self-contained push parser (H1Scanner, Pop3ServerLexer, SmtpServerLexer, FtpServerLexer, ImapServerLexer, the client-side reply lexers, the RESP parser in hopf-redis, and the frame parsers of H2, H3, WebSocket and MQTT) with its own token alphabet and bounded in-progress state.

  • One forward pass. Lexing and parsing happen together as the bytes arrive; there is no split-then-parse stage and no seeking back.
  • Tokens, not lines. A verb's argument is read according to its grammar as it arrives (SMTP paths and parameters, IMAP's per-verb grammar machines); CRLF is one production, not the only event boundary, and an argument is never held and searched again.
  • Bounded state. A parser keeps only what a token in progress needs, with a hard cap. What the parser has not consumed stays in the connection ring; it is never copied into a growing side buffer.
  • Semantic events out. Parsers push events to a handler as soon as they can be decided, and bodies stream through without being collected. Early parse state is not early application callbacks: a handler is told when a decision is due, not on every token.

Sibling incremental parsers (tractrix, rjsonparser, rmimeparser, rprotobuf) follow the same push model for XML, JSON, MIME and protobuf, and use the same loopbuf crate.

Telemetry

hopf-core defines the seams and nothing heavier: a TelemetryHook that the runtime, reactors and protocol crates call, structured LogRecords with a level axis, and the qlog event surface used by hopf-quic. A hook is installed per Runtime or process-wide. hopf-otel implements it with OTLP/HTTP and JSONL exporters, an access-log sink and a console sink on a batch worker that is off the reactor's hot path. See telemetry.

Testing

  • hopf_core::testing::Peer (Cargo feature testing) drives a ProtocolHandler in-process with no sockets and no reactor: it records what the handler sends, feeds it scripted input (text or binary), plays the part of the reactor for storage-pool and timer callbacks, and can make the connection secure or fail it.
  • Unit tests are hermetic: no network, no filesystem writes, no clock waits. scripts/check-hermetic-tests.sh runs them in a sandbox that fails any test doing socket or file I/O, and CI runs it.
  • Tests that need real sockets or files sit behind a per-crate integration feature, and interoperability is checked against independent peers (OpenSSL, GnuTLS, BIND, OpenLDAP, Redis and others) where one exists.

Security substrate

Encrypted transport and shared authentication crypto are part of hopf-core's contract, not a bolt-on crate graph. Handlers see plaintext and a SecurityInfo; how the bytes were protected is below the line.

Today

  • AWS-LC (BoringSSL lineage) is the native crypto library, reached through aws-lc-rs / aws-lc-sys. The fips feature builds its FIPS module, and RuntimeConfig::fips refuses to start without it.
  • TCP TLS / STARTTLS: in-tree TLS 1.2 and 1.3 in hopf-core::tls, AEAD cipher suites only (AES-GCM, ChaCha20-Poly1305; no CBC). TlsVariant (V13 / V12 / Negotiating) is driven by TcpConnection through TlsRecordSink; PEM and builder helpers return SharedTlsAcceptor / SharedTlsConnector wired with TcpListenerConfig::with_tls, with_starttls_acceptor or TcpConnectorConfig::with_tls. Features include hybrid post-quantum key exchange, ML-DSA signatures, session tickets with key rotation, Extended Master Secret, ALPN, key updates, certificate compression and Encrypted Client Hello.
  • QUIC / HTTP/3: in-tree RFC 9000 transport and its TLS 1.3 handshake for RFC 9001, both in hopf-quic on AWS-LC directly; no external QUIC or TLS library anywhere in the production dependency graph. H3 and QPACK are in-tree in hopf-http.
  • Mail and DNS authentication crypto: DKIM, ARC and DNSSEC call aws-lc-rs directly from protocol crates.
  • UDP: datagram handlers in core are cleartext. DTLS 1.2 and 1.3 sessions (hopf-core::dtls / dtls12) have a reactor-driven UDP driver and per-peer 1.3-vs-1.2 negotiation (DtlsVersionPolicy, mirroring TCP's TcpTlsVersionPolicy). No protocol crate dials or listens over DTLS yet; see Direction.

Direction

  • DTLS: expose sessions through the same generic Endpoint contract TCP TLS uses, so protocol crates can dial and listen over DTLS without bespoke wiring. The handshake and record engines and version negotiation are shipped; only this integration layer is outstanding.
  • Primitives: one trust and identity surface for X.509 (TLS/mTLS), DKIM/ARC signing, DNSSEC and future host-key models (SSH).
  • Auth: optional GSSAPI/Kerberos SASL on hopf-auth, once the native foundation is settled; KDC work stays on StorageExecutor.

Other transports (SSH/SFTP, DNSCrypt, CoAP/OSCORE) share the primitive layer but bring their own framing and key exchange; they are not TLS handshakes.

Status table: Conformance → Security substrate.

Explicit non-dependencies

Async app runtimes (Tokio et al.), Hyper, Axum, Tower, serde as architecture, the quinn / quinn-proto crates (fully replaced by hopf-quic's in-tree RFC 9000 transport), servlet/JSP/Java EE APIs, reflective XML DI, TOML/YAML as primary composition formats.

Non-goals

  • Replacing AWS-LC with multiple competing pure-Rust crypto stacks for TLS, DTLS and QUIC.
  • CBC cipher suites, ever: TLS 1.2 is AEAD-only.
  • OCSP stapling and revocation policy inside the handshake engine: certificate validation policy belongs to the caller, not to a synchronous handshake state machine.
  • A servlet container or Java EE APIs.
