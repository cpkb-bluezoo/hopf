Performance Audit

Hot-path allocation, copying, and locking behavior in hopf-core and the shared parsing substrate it hands to every protocol crate — read directly from source, not benchmarked. Companion to Conformance and Scalability (which covers cross-thread/cross-core contention; this page covers per-call cost on a single reactor).

Timer cancellation: bounded by periodic compaction

TimerQueue (crates/hopf-core/src/timer.rs) is a BinaryHeap — O(log n) schedule, and per-reactor with no lock (good, see Scalability). Cancellation itself stays lazy and cheap: schedule_with_cancel pushes an entry with a shared cancelled: Arc<AtomicBool> (timer.rs:79-104), and cancelling just flips that flag from whatever thread holds the handle — nothing walks the heap at cancel time, since the heap itself is only ever touched by the single reactor thread that owns it. purge_cancelled (timer.rs:146-154) and the skip-check in fire_due (timer.rs:132-144) only ever look at the top of the heap, so a cancelled entry buried anywhere else — including its captured Box<dyn FnOnce()> closure state — would otherwise stay allocated until it naturally bubbles to the top.

This matters because the established idiom for idle/keepalive timers throughout the protocol crates (see rearm_keepalive in hopf-mqtt's and hopf-pop3's control handlers) is cancel-and-reschedule on every read: cancel the old timer, schedule a new one further out — exactly the pattern that buries cancelled entries. schedule_with_cancel handles this at the one point that can see it growing: every call checks whether the heap has at least doubled since the last compaction (heap.len() >= compacted_len * 2, floored at COMPACT_MIN = 256 so small heaps aren't compacted needlessly, timer.rs:101-103) and if so rebuilds it via compact() (timer.rs:107-115), dropping every currently-cancelled entry in one O(n) pass. Worst-case heap size is bounded to roughly 2× the live-timer count rather than growing with cumulative read count for the life of a connection, and the O(n) cost is amortized across the O(n) schedule calls that grew it — the same amortized-doubling argument as a growable array, applied to lazy deletion instead of insertion.

Storage submission: no allocation to satisfy the borrow checker

StorageExecutor::submit_on (crates/hopf-core/src/storage.rs:125-176) decides accept-or-reject against a capacity gate — a single AtomicUsize CAS loop (storage.rs:138-153) comparing reserved-but-not-yet-completed jobs against capacity — before callback is moved anywhere. Since accept and reject are decided up front, exactly one of "the job runs" or "it's rejected" ever ends up owning callback, so it moves by value into whichever closure actually gets used (storage.rs:141 for reject, storage.rs:157-164 for the accepted job) — no Arc<Mutex<Option<_>>> wrapper needed to let two mutually-exclusive code paths both potentially claim it. Submission no longer goes through a bounded mpsc::sync_channel either — capacity is the CAS gate's job now, so the channel itself is unbounded (storage.rs:85) and a reserved job's send essentially never blocks or fails on capacity grounds.

The capacity gate has to reproduce the old bounded-channel's actual semantics precisely: a job a worker has already dequeued no longer counts against a channel's buffer, so the effective ceiling was always threads running concurrently plus queue_capacity buffered, not queue_capacity alone (storage.rs:101-106). Getting that wrong would silently shrink real workloads' effective concurrency; storage_capacity_is_threads_plus_queue_capacity in crates/hopf-core/src/lib.rs pins the exact boundary down. storage_worker (storage.rs:192-206) also now runs each job inside catch_unwind, so a panicking op or callback can't shrink the pool by one thread — which is what makes the capacity gate's assumption (the channel can't disconnect while any worker is alive) actually hold, rather than just being usually true.

Buffer compaction cost after partial consumption

deliver_plaintext_buffer / deliver_app_in (crates/hopf-core/src/connection.rs:366-420) hand the handler the buffered bytes, then compact with buf.drain(..consumed) (connection.rs:379-381, 407-409) — an O(remaining bytes) memmove of everything after the consumed prefix. In the common case (the handler consumes everything available each call) remaining is ~0 and this is free. It's only costly when a handler deliberately leaves a large amount buffered across many reads — e.g. streaming a large IMAP literal or MQTT PUBLISH payload one small chunk at a time while the bulk of an already-arrived body sits unconsumed waiting for more of the same message — in which case each read re-shifts that same trailing residue down. Cost is proportional to already-seen-but-unconsumed bytes, and is bounded by whatever a protocol's own streaming design chooses to leave buffered rather than being universal.

What's actually right

For balance — these are deliberate, correct choices worth keeping, not accidents:

  • No memset on read. read_from_socket (connection.rs:257-291) uses unsafe { self.net_in.set_len(cap) } to expose spare buffer capacity to Read::read without zeroing it first — a common, deliberate micro-optimization (the socket read only ever writes into that region; length is reset correctly on every early-return path including WouldBlock and error).
  • Power-of-two buffer growth with pool return. Every buffer grow (prepare_net_in, flush_tls_outbound, append_out — connection.rs:233-255,422-467,598-624) rounds up to a power of two, acquires from the pool, copies the live prefix, and returns the old buffer to the pool rather than dropping it — this is the buffer pool actually doing its job for the TCP path.
  • Panic isolation at every handler callback, not just receive() — connected, security_established, disconnected, error, and write_ready callbacks are all wrapped in catch_unwind (connection.rs:511-569, 494-506), confirming the "panic isolation at connection boundary" design claim holds for the whole callback surface, not a subset.
  • Lock-free quota counters. CounterQuota (crates/hopf-core/src/quota.rs:44-95) uses plain AtomicU64 with Relaxed ordering — correct here since each axis (in/out/messages) is an independent monotonic counter with no cross-axis ordering requirement, and it avoids a lock on what could otherwise be a very hot per-message path.
  • O(log n) timer scheduling, bounded under cancellation. TimerQueue is a proper binary heap, not a linear scan, per-reactor with no cross-thread lock on the hot scheduling path, and periodic compaction (§) keeps cancelled entries from accumulating under the cancel-and-reschedule idiom common to keepalive timers.
  • Zero-allocation UDP receive. handle_udp_readable (crates/hopf-core/src/reactor.rs:222-240) reads into a stack buffer and hands UdpDatagramHandler::on_datagram a borrowed slice straight into it (reactor.rs:233) — no heap allocation at all, not even a pooled one, since the trait only ever takes &[u8] and never needs ownership beyond the call.
