Method

Sourced from crates/hopf-core/src/{byte_stream_lexer,timer,storage,connection,reactor,bufpool}.rs, file:line cited throughout. This identifies mechanisms that cost more than they need to, with the actual code path that causes it — it is not a profiling result, and no number here ("O(n²)", "one extra allocation") was measured with a benchmark; each is a direct reading of what the code does per call.

Fixed: quadratic re-scan on fragmented tokens

Status: fixed. ByteStreamLexer (crates/hopf-core/src/byte_stream_lexer.rs) is the shared per-byte command/line lexer behind every line-oriented protocol in the workspace — SMTP, POP3, IMAP, FTP, and HTTP/1.1 request-line/header parsing all build a ByteStreamScanner on top of it (per the module's own doc comment, byte_stream_lexer.rs:5).

The bug, as originally found: feed() always started scanning its caller-supplied buffer from index 0. When a structured token (Mode::Token — a command verb, a header field-name, a single-character delimiter) was incomplete at the end of a call, the lexer rewound and handed the caller back the unconsumed slice to retain and re-supply, exactly as designed — but on the next call, it re-scanned that entire retained prefix from byte 0 again, calling ByteStreamScanner::consume() once per byte for bytes it had already consumed in every prior call. For a token of length L arriving across k separate reads, that's O(L·k) total consume() calls instead of O(L) — quadratic in the pathological case of one byte per read, which a slow or adversarial sender can force cheaply and repeatedly against every protocol built on this lexer.

Correction from the original write-up: only Mode::Token had this shape. Mode::Text (header/argument values, latched after a delimiter) and Mode::RawFixed (IMAP literals, fixed-length passthrough) already deliver their bytes in chunks via text_token/raw_bytes as they arrive, without ever rewinding — they carry the bulk of a typical line's bytes and were never affected. The quadratic cost was real but narrower than first described: it applied to the short, delimiter-terminated pieces (a verb, a field-name), not whole lines or bodies.

The fix (byte_stream_lexer.rs): the lexer now remembers how far into the current in-progress token it already scanned (resume_len), and resumes exactly there on the next call instead of restarting at 0 — the scanner's own per-byte state (e.g. a POP3 scanner's "last byte was CR" flag) already persisted correctly across calls, so once `feed()` stops re-deriving its position from scratch each time, each byte is visited exactly once for the lifetime of one token, regardless of how many reads it's split across. The caller-facing contract (retain the unconsumed suffix, re-supply it next call) is unchanged — every one of the five dependent protocol crates already followed that contract correctly, so no caller needed to change. A regression test (feeding_one_byte_at_a_time_scans_each_byte_exactly_once) feeds a 53-byte line one byte at a time and asserts exactly 53 consume() calls total, not the 1,431 the quadratic version would have produced.

Verified against the full workspace test suite plus real-socket integration tests for all five dependent crates (hopf-pop3, hopf-smtp, hopf-ftp, hopf-imap, hopf-http) — all passing.

Timer cancellation doesn't reclaim heap space

TimerQueue (crates/hopf-core/src/timer.rs) is a correct BinaryHeap — O(log n) schedule, and per-reactor with no lock (good, see Scalability). But cancellation is lazy: schedule_with_cancel pushes an entry with a shared cancelled: Arc<AtomicBool> (timer.rs:70-83), and cancelling just flips that flag — nothing removes the entry from the heap. purge_cancelled (timer.rs:113-121) and the skip-check in fire_due (timer.rs:99-111) only ever look at the top of the heap; a cancelled entry buried anywhere else stays allocated — including its captured Box<dyn FnOnce()> closure state — until it naturally bubbles to the top, which happens only when everything scheduled before its original deadline has fired or been popped.

This matters because the established idiom for idle/keepalive timers throughout the protocol crates (see rearm_keepalive in hopf-mqtt's and hopf-pop3's control handlers) is cancel-and-reschedule on every read: cancel the old timer, schedule a new one further out. A connection that's chatty (many small reads, each rearming keepalive) accumulates one dead heap entry per read for the lifetime of the connection, all holding onto their closure captures (typically a cloned ConnHandle or similar) until the original un-rearmed deadline would have arrived — which, for a repeatedly-rearmed keepalive timer, could be long after the entry became irrelevant. Heap memory use for a busy reactor therefore grows with read count, not with the number of live timers, until enough real firings happen to drain the accumulated dead entries.

One unnecessary allocation per storage submission

StorageExecutor::submit_on (crates/hopf-core/src/storage.rs:111-152) wraps every callback in Arc::new(Mutex::new(Some(callback))) (storage.rs:118) so it can be invoked from either of two places: inside the job closure on success, or immediately on rejection. But those two paths are mutually exclusive by construction — try_send (storage.rs:136) either succeeds (only the job-internal path ever runs) or fails (only the rejection path runs, and the job closure that captured the Arc<Mutex<..>> is dropped unused). The Arc/Mutex pairing exists only to satisfy the borrow checker across that either/or split, not because the callback is genuinely shared or contended — every submission pays for a heap allocation and a lock/unlock that a restructured call (check success/failure before building the job closure, rather than building both branches unconditionally) wouldn't need. Not hot in the sense of "per byte" — this is once per blocking-work submission — but it's easy to avoid and the pattern is worth not copying elsewhere.

Buffer compaction cost after partial consumption

deliver_plaintext_buffer / deliver_app_in (crates/hopf-core/src/connection.rs:366-420) hand the handler the buffered bytes, then compact with buf.drain(..consumed) (connection.rs:379-381, 407-409) — an O(remaining bytes) memmove of everything after the consumed prefix. In the common case (the handler consumes everything available each call) remaining is ~0 and this is free. It's only costly when a handler deliberately leaves a large amount buffered across many reads — e.g. streaming a large IMAP literal or MQTT PUBLISH payload one small chunk at a time while the bulk of an already-arrived body sits unconsumed waiting for more of the same message — in which case each read re-shifts that same trailing residue down. This is the same underlying shape as the lexer finding above (repeated work proportional to already-seen bytes) but scoped to raw/streaming consumption rather than structured tokens, and is bounded by whatever a protocol's own streaming design chooses to leave buffered rather than being universal.

UDP datagrams bypass the buffer pool

Reactor::handle_udp_readable (crates/hopf-core/src/reactor.rs:221-238) reads into a stack buffer, then does let data = buf[..n].to_vec(); (reactor.rs:229) — a fresh heap allocation and copy per datagram, never drawn from or returned to the same Arc<BufferPool> that every TCP connection's net_in/net_out uses (Scalability §Buffer pool). For hopf-dns's UDP-heavy workload in particular, this means the one transport that arguably sends/receives the most discrete messages per second in the framework is the one place not benefiting from buffer reuse. Not necessarily wrong — datagrams are typically small (a DNS query/response fits in one MTU) and short-lived — but it's an inconsistency worth noting: the pooling discipline built for TCP doesn't extend to UDP.

What's actually right

For balance — these are deliberate, correct choices worth keeping, not accidents:

  • No memset on read. read_from_socket (connection.rs:257-291) uses unsafe { self.net_in.set_len(cap) } to expose spare buffer capacity to Read::read without zeroing it first — a common, deliberate micro-optimization (the socket read only ever writes into that region; length is reset correctly on every early-return path including WouldBlock and error).
  • Power-of-two buffer growth with pool return. Every buffer grow (prepare_net_in, flush_tls_outbound, append_out — connection.rs:233-255,422-467,598-624) rounds up to a power of two, acquires from the pool, copies the live prefix, and returns the old buffer to the pool rather than dropping it — this is the buffer pool actually doing its job for the TCP path.
  • Panic isolation at every handler callback, not just receive() — connected, security_established, disconnected, error, and write_ready callbacks are all wrapped in catch_unwind (connection.rs:511-569, 494-506), confirming the "panic isolation at connection boundary" design claim holds for the whole callback surface, not a subset.
  • Lock-free quota counters. CounterQuota (crates/hopf-core/src/quota.rs:44-95) uses plain AtomicU64 with Relaxed ordering — correct here since each axis (in/out/messages) is an independent monotonic counter with no cross-axis ordering requirement, and it avoids a lock on what could otherwise be a very hot per-message path.
  • O(log n) timer scheduling. Aside from the lazy-cancellation caveat above, TimerQueue is a proper binary heap, not a linear scan, and is per-reactor with no cross-thread lock on the hot scheduling path.
