gRPC

Crate hopf-grpc: unary and streaming gRPC over hopf-http Streams. Uses a runtime .proto model (rprotobuf) - no generated stubs or codegen. Works wherever Hopf Streams run (HTTP/2 preferred; H1/H3 inherit Stream framing, with H1 trailer caveats).

#![forbid(unsafe_code)].

Standards

Topic Detail
Transport gRPC over HTTP (application/grpc), typically HTTP/2
Path POST /{service}/{method}
Message 5-byte prefix: 1-byte compression flag + 4-byte big-endian length
Status grpc-status / grpc-message in trailers (or headers)
TE te: trailers
Protobuf proto2 / proto3 via rprotobuf
Status codes e.g. 4 DEADLINE_EXCEEDED, 8 RESOURCE_EXHAUSTED, 12 UNIMPLEMENTED, 13 INTERNAL
Compression Per-message, named by grpc-encoding, advertised in grpc-accept-encoding: gzip and deflate by default, br opt-in
Deadlines grpc-timeout sent by the client and enforced on both sides
Metadata Custom headers and trailers, including -bin (base64) keys

Content-types accepted: application/grpc, application/grpc+proto, and application/grpc+json (optional ; parameters). Other subtypes (+thrift, grpc-web*, …) return HTTP 415. JSON payloads use the proto3 JSON mapping via rjsonparser, including nested, repeated and map fields and the well-known types (Timestamp, Duration, FieldMask, the wrappers, Struct/Value/ListValue); framing stays 5-byte length-prefixed.

Architecture

HTTP Stream
    │ POST /pkg.Service/Method  content-type: application/grpc
    ▼
GrpcHandlerFactory  (ServerHandlerFactory)
    │ ProtoFile::get_rpc_by_path
    ▼
GrpcService::start_call (or start_unary_call) → GrpcCallHandler
    │
    └── GrpcCall (GrpcResponseChannel) → framed responses + grpc-status trailers

Client path: GrpcClient::unary_call → GrpcUnaryCall as ClientHandlerFactory for an HTTP client endpoint. For a streaming method, GrpcClient::streaming_call returns the factory and a GrpcClientCall whose send / half_close / cancel drive the request side from any thread; each response message arrives through GrpcResponseHandler::start_message, and on_complete reports the call's final status once.

Framing

Type / const Purpose
GrpcFrameParser<H> Incremental length-prefixed parser
GrpcEventHandler Message callbacks
frame(&[u8]) -> Vec<u8> Encode one message
framed_size Size helper
DEFAULT_MAX_MESSAGE_SIZE 4 MiB
GrpcFramingError Oversized / invalid flag / partial

Flag 1 marks a message compressed with the call's grpc-encoding; frame_compressed writes one. The parser passes the flag on and the server and client decode with the negotiated algorithm (a flag above 1 is not gRPC and fails the call). Split-feed safe. 0 max size uses the default 4 MiB (not unlimited); pass u64::MAX only for an explicit no-cap.

Streaming RPCs

A unary-only service implements start_unary_call. A service that serves client-, server- or bidirectional-streaming methods implements start_call and returns true from streaming_supported (otherwise a streaming method is answered UNIMPLEMENTED):

pub trait GrpcService: Send + Sync {
    fn start_unary_call(&self, path: &str, response: GrpcResponseChannel)
        -> Option<Box<dyn ProtoMessageHandler>> { None }
    fn start_call(&self, path: &str, call: GrpcCall)
        -> Option<Box<dyn GrpcCallHandler>>;   // default: wraps start_unary_call
    fn streaming_supported(&self) -> bool { false }
}

pub trait GrpcCallHandler: ProtoMessageHandler {
    fn end_requests(&mut self) {}   // client half-closed
    fn cancelled(&mut self) {}      // stream reset, connection gone, or deadline passed
}

Request messages arrive as ProtoMessageHandler events, one start_message / end_message pair each. GrpcCall is the GrpcResponseChannel for the call; it is Clone and may be used from any thread. Send any number of messages with open_message … complete, then end the call with close() (status 0) or close_with(status, message). pause_requests / resume_requests apply read backpressure.

Metadata, peer and deadlines

GrpcResponseChannel methodPurpose
request_metadata()GrpcMetadata the client sent (protocol headers excluded)
with_response_metadata(|m| ...) / with_trailing_metadata(|m| ...)Set initial (header) and trailing metadata
deadline()Client deadline from grpc-timeout, if any
connection_info()Peer address and TLS details (hopf_http::ConnectionInfo)

GrpcMetadata keeps keys in order; add / get / get_all handle text values and add_binary / get_binary handle -bin keys (base64 on the wire). Reserved protocol keys are refused with MetadataError. When a request's deadline passes before the call ends, the server closes it with DEADLINE_EXCEEDED and calls cancelled.

Responding

// Inside handler after decoding request fields:
let mut msg = channel.open_message(None)?; // content-type optional
msg.field("message", ScalarValue::String("hello".into()));
// or msg.writer() / msg.serializer()
msg.complete()?;

// Errors:
channel.send_error(12, "UNIMPLEMENTED");
channel.send_error_cause(&err);

Server maps protocol problems to HTTP 415 / 404 / 400, or gRPC status in trailers. A unary call takes one response message (response already sent if repeated); a streaming call takes any number until it is closed.

Client

use hopf_grpc::GrpcClient;

let client = GrpcClient::new(proto_file);
let call = client.unary_call(
    "/helloworld.Greeter/SayHello",
    req_bytes,
    Box::new(MyResponseHandler),
);
// or client.unary_call_json(...) for application/grpc+json
// `call` is a ClientHandlerFactory - attach to H2/H1/H3 client endpoint
Type Role
GrpcClient Holds ProtoFile
GrpcUnaryCall ClientHandlerFactory for one unary call
GrpcStreamingCall / GrpcClientCall ClientHandlerFactory for one streaming call, and the handle that sends its request messages
GrpcResponseHandler App callback for response / status

GrpcResponseHandler receives start_message per response message, on_initial_metadata / on_trailing_metadata, on_grpc_status from headers or trailers, and on_complete(status, message) exactly once per call, including when the call fails locally (UNAVAILABLE, INTERNAL, RESOURCE_EXHAUSTED, DEADLINE_EXCEEDED).

GrpcClient::encodings(&[ContentCoding])Codings decoded in responses and offered in grpc-accept-encoding (default gzip, deflate)

Limitations

  • No generated stubs - runtime .proto model only.
  • H1 trailer support is limited (inherited from hopf-http); prefer H2/H3.
  • One message per unary response enforced.
  • br message compression is a non-standard extension; it is only offered or used when both peers enable it.
  • Not a full Google gRPC stack (no interceptors, load balancing, etc.).
